## 逐题详情

### 002 ❌ 数据文件损坏（std 正确）
- `data/04.in ~ 10.in` 共 7 个点 std 输出与 `.out` 不符。
- 独立用 Python 大整数验证 std 答案**全部正确**（如 `n=1→0`、`n=2→2`、`n=8→10`、`n=1000000000→350704366`）。
- `.out` 内容明显陈旧/错乱：不同输入对应相同输出（04 与 05 均为 `478361013020`）、`n=8` 的答案竟是 `350704366`（`n=10^9` 的量级）、首行还有 `0`。
- **处理建议**：用 `make data` 重新生成 `002/data/`。

### 003 ⚠️ 题面标题错误
- `statement.md` 标题为"$3$ 或 $5$ 的倍数"（001 的标题），实际内容是求最大质因数（对应 PE 3）。样例 `13195 → 29` 正确。
- **处理建议**：改标题为"最大质因数"。

### 004 ⚠️ 题面样例缺失
- 输入格式为"无"（原题未参数化，符合项目早期设定），但"样例"一节完全为空。
- **处理建议**：补一个无输入样例（输出 `906609`）。

### 005 ✅
- 数据全部吻合，最大耗时 0.349s（T=1e4 满组时仍 < 0.5s）。

### 006 ❌ 正确性 bug（数据未覆盖到边界所以未暴露）
- 题面允许 $K \le 10^5$，但 `sum*sum` 在 $K \gtrsim 77930$ 时超出 long long。
- 边界实测：`K=100000` 时 std 输出 `6553422590457098384`，真值（Python 大整数）为 `25000166664166650000` —— 真值本身已超过 `unsigned long long` 上限，必须用 `__int128` 或大数输出。
- 另：`数据范围` 一节只写了一个"K"字（约束在输入格式一节有，但排版残缺）。
- **处理建议**：改用 `__int128` 输出（答案 < 2^127），并修数据范围排版。

### 007 ❌ 坏数据 + 边界性能风险
- `data/2.in`：`T=10000`，K 从 **0** 到 9999 —— K=0 违反题面约束（$1 \le K$），且 std 对 K=0 会执行 `primes[k-1]`（即 `primes[-1]`，数组越界 UB）。对应 `.out` 首行 `148948139` 与任何合法 K 的答案都对不上（陈旧数据）。
- 耗时：data 上最大 1.973s；题面上界 $K=10^7$ 实测 **1.85s**、内存约 230MB（筛表 1.9×10^8）。答案 `179424673` 与已知的第 10^7 个素数一致（正确性没问题）。
- 题面未声明时限；`eval.sh` 按旧惯例 1s 计时——按 1s 标准则极限数据 TLE。
- **处理建议**：剔除/修正 K=0 数据点并重新生成 `007/data/`；题面明确时限（≥2s）或说明 $K \le 10^6$。

### 008 ⚠️ 题面样例错误 + 约束自相矛盾
- 样例第二组 `L=5, K=3, S=36791`：连续 3 位最大乘积应为 `6×7×9=378`，题面却写 `126`（那是前 3 位的乘积）。std 与 data 均为 378，题面错。
- 约束矛盾：题面描述与输入格式写 $K \le \min(L,100)$，`数据范围` 一节写 $K \le \min(L,15)$，gen.cpp 按 15 生成。代码本身对两者都适用，但题面必须统一。
- **处理建议**：样例输出改为 `378`；约束统一为 `min(L,100)`（代码已支持）。

### 009 ⚠️ SPJ 题没有 checker
- 题面承诺"如果存在多个解，输出任意一个"，但 `code/` 中没有任何 special judge / checker，`data/*.out` 只是 std 的固定选择。
- 算法本身正确（枚举 m>n 的 Euclid 公式覆盖所有勾股三元组；样例 `12→60`、`11→0` 正确）。
- **处理建议**：要么补一个 SPJ checker，要么把题面改为"输出 std 的那个解"（如最小字典序/最小 n）使其可普通比较。

### 010 ✅
- 数据全部吻合（`K=1→0`、`K=10→17` 等边界均正确），最大耗时 0.055s。

## 基础设施问题（影响所有题目）

1. `eval.sh` 依赖 `python3` —— Windows/本机只有 `python`，脚本直接失败；且超时硬编码 1s。
2. `scripts/check.sh` 是死循环对拍（直到 WA 才停），AC 时永不退出，不适合自动化。
3. 各题 `statement.md` 均未声明时限/内存限制，耗时合格与否只能按惯例（1s/256MB）判断。
4. 以上由 `_tools/audit/audit.py` 绕过（直接驱动 g++ 与 std），后续全量审计沿用此路径。
